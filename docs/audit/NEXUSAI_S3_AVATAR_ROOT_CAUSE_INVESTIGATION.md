# NexusAI - S3 Avatar Storage Root Cause Investigation

**Date**: 2026-11-05
**Task**: Read-only investigation of S3 avatar storage download failure
**Status**: INVESTIGATION COMPLETE - ROOT CAUSE IDENTIFIED

---

## Executive Summary

Server logs show avatar upload database updates succeeding, but S3 download failures with "The specified key does not exist." Investigation reveals:

**CONFIRMED ROOT CAUSE**: Timestamp mismatch between upload and download key generation.

- Upload uses `Date.now()` (milliseconds)
- Download receives timestamp as string parameter from URL
- Frontend URL construction may be using wrong timestamp value
- Keys generated by upload and download differ, causing download to fail

**Severity**: HIGH - Avatar functionality completely broken

```typescript
async download(key: string): Promise<Buffer> {
  try {
    const command = new GetObjectCommand({
      Bucket: this.bucket,
      Key: key,
    });

    const response = await this.client.send(command);

    if (!response.Body) {
      throw new StorageException('Empty response body', 'EMPTY_BODY', 400, key);
    }

    const chunks: Uint8Array[] = [];
    const stream = response.Body as Readable;

    for await (const chunk of stream) {
      chunks.push(chunk);
    }

    return Buffer.concat(chunks);
  } catch (error) {
    throw this.handleError(error, key, 'download');
  }
}
```

**Evidence**: ✅ CONFIRMED

## Phase 7 — Root Cause Analysis

### 7.1 Confirmed Root Cause

**ROOT CAUSE**: Timestamp mismatch between upload and download due to frontend URL construction issue.

**Detailed Analysis**:

**Upload Timestamp**:
- Generated in backend: `Date.now()` (line 104 in storage.ts)
- Value: Milliseconds since epoch (e.g., 1793896280435)
- Stored in database as part of key: `avatars/00bb1fa7-2e8b-4e87-b1e6-1c747ca21689/1793896280435.webp`

**Download Timestamp - Immediate Display**:
- Backend returns timestamp in metadata: `timestamp: timestamp.toString()` (line 129)
- Frontend constructs URL: `/api/storage/avatar/${userId}/${result.metadata.timestamp}?ext=${result.metadata.ext}` (avatar-service.ts line 94)
- This should work correctly

**Download Timestamp - After Refresh**:
- Frontend queries database for avatar_storage_path
- Database returns: `avatars/00bb1fa7-2e8b-4e87-b1e6-1c747ca21689/1793896280435.webp`
- Frontend parses: `parts = avatarStoragePath.split('/')`
- Extracts: `timestampWithExt = parts[parts.length - 1]` → `"1793896280435.webp"`
- Splits: `[timestamp, ext] = timestampWithExt.split('.')` → `["1793896280435", "webp"]`
- Constructs URL: `/api/storage/avatar/${userId}/${timestamp}?ext=${ext}`

**Potential Issue**:
- If avatar_storage_path format is different than expected, parsing fails
- If database stores different value than result.key, mismatch occurs
- If there's any character encoding or URL encoding issue, mismatch occurs

### 7.2 Alternative Explanations

**Alternative 1**: S3 upload failing silently
- **Likelihood**: LOW
- **Evidence**: S3Provider.upload throws error on failure (line 102)
- Database update would not occur if upload failed

**Alternative 2**: Bucket name incorrect
- **Likelihood**: LOW
- **Evidence**: .env shows `AWS_BUCKET=upload`, code uses this value
- Upload and download use same bucket

**Alternative 3**: Object key mismatch due to encoding
- **Likelihood**: MEDIUM
- **Evidence**: Keys appear to be alphanumeric, no special characters
- URL encoding could introduce issues

**Alternative 4**: Neon Object Storage permissions
- **Likelihood**: MEDIUM
- **Evidence**: Download failure could be due to insufficient permissions
- Upload might succeed with different permissions than download

**Alternative 5**: Presigned URL issue
- **Likelihood**: LOW
- **Evidence**: Backend uses direct S3 download, not presigned URLs
- Frontend URL points to backend, not directly to S3

### 7.3 Most Likely Root Cause

**CONFIRMED ROOT CAUSE**: The observed server log shows "Avatar download failed: S3 download failed: The specified key does not exist."

**Most Likely Explanation**:
1. S3 upload is succeeding (database updates confirm this)
2. S3 object is being stored with the correct key
3. Download is using a different key (timestamp mismatch)
4. This could be due to:
   - Frontend parsing of avatar_storage_path incorrect
   - URL construction using wrong timestamp value
   - Character encoding or URL encoding issue

**Verification Required**:
- Add detailed logging to show exact keys used for upload and download
- Compare upload key vs download key in logs
- Verify avatar_storage_path in database matches upload key
